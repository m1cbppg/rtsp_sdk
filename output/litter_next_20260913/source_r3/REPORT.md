## 30分钟任务为何停止

只读查询已有生产流`bd1b5e85ab6442eb82631e1680092c0f`时，API返回`pipeline_healthy=false`及约0.0466 FPS；为遵守不影响生产的约束，停止了仅挂载`/tmp/litter_source_30m_1021_20260913`的试验容器（`2c03738ce5d2…`，`festive_archimedes`）。停止于UTC 09:59:22，即北京时间17:59:22。

进一步核查发现生产指标最后更新于**北京时间12:16:57（UTC 04:16:57）**，逐流JSONL的修改时间也停在该时刻，早于这次30分钟试验。故0.0466不能作为当前帧率，既不能归因于本次取流试验，也不能据此宣称生产当前健康。后续多次查询仍为相同旧值；只有容器ID、启动时间和重启次数保持不变有实时证据。

旧探针仅在结束时写摘要，停止后没有留下这次30分钟任务的统计结果。因此本次记为**中断、无完整统计**，不拼接10分钟/60秒数据冒充30分钟通过。容器日志保留在`interrupted_30m.log`。生产容器未重启、未改配置、未删除或重建其流。

## 生产流故障证据与勘误

已证实的是worker连续输出 `Could not receive message (Received end-of-file)` 和 `Resetting source`，指标文件陈旧，API仍返回`status=running`。这表示进程存在，不代表视频健康。**撤回“地址已过期约25小时、根因确定”的判断**：`TimeStamp`可能是签发/签名时间，没有接口到期语义或上游鉴权响应，不能由时间早于现在推导到期。EOF的根因仍未确定；内部MediaMTX的401也不能当作上游鉴权失败证据。

现有任务的输入设备编号不在用户提供的五路设备中；缺少证据认定其业务用途为“旧演示流”。1021通过自己的设备接口取址并实测是否可读。`inspect_rtsp_url_expiry`已改为只报告脱敏时间提示，到期状态保持未知，不据此拒绝URL，也不把未来时间称为可用。生产API和现有任务未修改。

## 实现改动

| 文件 | 作用 |
| --- | --- |
| `ground_litter_source.py` | 默认关闭的有界解码诊断环，记录每个解码帧的到达时钟、PTS、读取耗时、关键帧和坏帧标志；生产者不等待诊断锁，覆盖/争锁计数可见。直播画面年龄从解码完成起算，包含颜色转换时间；时间戳提示不推断URL到期 |
| `probe_ground_litter_source.py` | 显式要求PyAV，缺失时在取流前退出；每5秒原子保存进度、分开记录邮箱采样和推理、源能力与文件指纹；诊断最多2048条在途记录和120,000条落盘记录；支持SIGTERM/SIGINT安全结束并写报告 |
| `guard_ground_litter_source_probe.py` | 启动前及运行中检查生产容器、流集合、帧率、健康和指标是否新鲜；CPU 1.5核、内存1GiB、无GPU挂载，以宿主目录所属用户运行。生产异常/指标超过30秒未更新时只停止唯一命名的测试容器，保留诊断 |
| `Dockerfile.ground-litter-source-probe` | 单独的PyAV16.1.0离线诊断镜像；不更改正式镜像标签，依赖wheel与源码均有SHA-256 |

最初停止复测暴露了信号处理函数中调用`multiprocessing.Event.set()`导致的锁重入卡住；修正后，信号函数只记录请求，由主循环设置停止事件和清理子进程。故障用例和修复后的结果都保留。
