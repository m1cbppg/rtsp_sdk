## 1. 目标与边界

设备：`44180209031322001021`、`01022`、`01027`、`01028`、`01030`。先对每路全部可用回放做元数据清点，再分层下载 PS，产生高召回候选事件卡片。用户只判断“垃圾 / 非垃圾 / 框不准 / 看不清”；系统负责候选框、去重、关键帧、结果保存和后续标签传播。

本阶段不训练正式模型、不接入实时流、不修改或重启生产容器。旧 Profile v6 草稿保持原样。

## 2. 实施顺序

1. 新增独立审计模块和 CLI，不修改暂停中的 Profile Factory 文件；
2. 单元测试冻结：录像分层选择、跨帧候选聚合、候选配额、路径与敏感字段、审核数据指纹；
3. 服务器 `~/ground-litter-audit` 隔离目录部署；
4. 先跑 `01030` 一天试点：清单 → 代表文件 → 抽帧 → 候选 → 事件卡；
5. 下载试点产物回本地，人工检查图片与数据结构；
6. 为其余四路拉代表帧，制作独立 ROI/扩展路面区；
7. 扩展到五路全部可用七天，并按检查点持续写出；
8. 只传回 JPEG/WebP、JSONL、报告和校验和，服务器 PS 处理后删除；
9. 启动本地只读静态资源 + 审核结果 API，提供 `127.0.0.1` 网页。

## 3. 候选来源

- `semantic`：Turhancan 低阈值 ROI/扩展区分块；
- `generic`：YOLO26 COCO 物体候选；
- `temporal`：同机位相邻代表帧的新增/消失连通域；
- `objectness`：类别无关的局部边缘/连通区域；
- `grid`：ROI/扩展路面区多尺度系统网格；
- `random_audit`：不按模型排序的随机覆盖。

候选不是自动正标签。所有来源映射为统一候选记录，按摄像头、时间、位置和外观去重；来源配额确保模型候选不能挤掉 grid/random。

## 4. 录像抽样与资源上限

清单覆盖所有文件。像素第一轮每 30 分钟选一个 PS，每个文件抽开始/中间/结束三帧；未入选文件再做 5% 稳定随机抽样。候选时段按需补拉相邻文件。每个 PS 使用临时租约，产物原子落盘后立即删除。

初始上限：raw 峰值 4 GiB、审核产物 20 GiB、每设备第一轮最多 600 文件、候选事件卡默认最多 600 张。所有上限和截断原因写报告，不静默丢数据。

## 5. 审核资产

每张卡至少包含上下文框图、候选放大图、同一位置前/当前/后关键帧（存在时）、设备/时间/来源/原生像素尺寸/区域。审核结果逐条写服务器本地无关的 JSON 文件，并可导出；浏览器 localStorage 只作缓存。

审核数据按批次发布且带 SHA-256 指纹。替换数据集时不能沿用旧结果。路径必须位于仓库审核资产根目录，签名 URL、API 密钥和摄像头密码不得进入任何产物。

## 6. 试点验收

- 录像清单无签名 URL；
- PS 临时文件退出后为 0；
- 代表帧时间不是 PS 原始 PTS 基值；
- ROI/扩展区坐标正确，候选框不越界；
- semantic、temporal、grid、random 至少能各形成或明确报告 0 条；
- 同一固定对象不会按每帧重复成卡；
- 本地审核页可用键盘快速分类，结果可导入/导出且指纹校验；
- 生产容器 ID、启动时间和镜像不变。

试点不满足上述条件时不启动五路长任务。完整运行设置 24 小时硬检查点，不无限失败重跑。
