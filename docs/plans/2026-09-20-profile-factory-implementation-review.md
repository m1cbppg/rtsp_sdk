# Profile Factory 方案一实施评审（2026-09-20）

## 结论与范围

**本次验收不通过。** 工程链路已经能够取得素材、解码、生成并发布 Bank，但当前实现不能用来证明“自动得到 N 个适合实际识别的 Profile”。构建集动态回放、独立盲测、覆盖率及小目标验证存在会改变结论的错误。`camera_01030/v1` 应保留为可追溯实验产物，暂不作为方案二生产接入的已验收基线。

这不是要求零误报、100% 覆盖或绝对干净的背景。用户允许七天持续存在的物体进入背景，也允许少量残余误差。本次阻塞来自算法与验收证据不一致，不能通过缩小 ROI、增加样本或放宽业务容差代替修复。

本次依据方案一、运行时 Selector 方案和现有实现进行代码审查、本地复现、服务器只读核对。没有修改实现、重建 Bank、下载录像、部署或重启容器。未进行在线负载和识别准确率验收。

## 必须修复的发现

### R1 / P1：盲测输入参与校准，发布的 Bank 又没有保存实际校准结果

位置：`scripts/evaluate_ground_litter_profile_bank.py:141`、`:543`；`scripts/build_ground_litter_profile_bank.py:1233`。

评估器直接把 `args.input` 传入 `_calibration_scores()`，从同一待评目录的首个可读文件取最多 12 帧，为所有 Profile 重新估计进入/保持包络，随后评估这个目录。09-20 没参与背景合成不等于独立盲测：它已经参与了阈值拟合。

发布时又使用 `default_matcher_config()`，没有冻结建库测得的各 Profile 包络。服务器 `matcher.json` 标记 `uncalibrated_defaults`，默认进入/保持阈值为 1.6/2.2；建库报告进入阈值约 6.36–11.20，评估报告又产生约 8.6–11.8 的另一组阈值。盲测中的最优分数约 7.18–9.04。当前评估收益不能直接归因于发布的 Bank，运行时照资产加载也不能复现评估条件。

修复：只从明确隔离的校准集拟合；把包络、尺度、来源及配置哈希一起发布。盲测只读冻结资产，禁止任何形式的现场重估阈值。修复后使用未参与拟合的新时间段复验；已用于调参的 09-20 数据可作为回归集。

### R2 / P1：构建集“动态回放”评分没有使用当前帧，N 实际受静态前 16 截断支配

位置：`scripts/build_ground_litter_profile_bank.py:797`、`:812`、`:842`、`:901`、`:925`、`:1328`。

`stage_preselect()` 遍历当前回放帧，却给每个 Profile 使用其各自 `evaluation_frames` 循环取出的历史帧。缺少来源映射时还按顺序轮转分配帧。同一 tick 的 Profile 并非面对同一场景。回放时间用帧索引代替原始时间，素材仅取每个文件开头少量连续帧，真实环境转场、长缺口均不保留。

反例输入 6 帧，像素标记分别为 10/20/30/40/50/60：6 个 tick 中 p1 始终评分 50，p2 始终评分 60，完全没有对输入序列做公平比较。

评分前硬编码静态排名前 16；`_prune_candidates()` 仅检查静态覆盖和低支持标记，最后 `del selector`，没有做删除后的动态重放。反例传入根本不是 Selector 的对象，剪枝仍正常执行。服务器 36 个外观组生成 23 个候选，再取前 16。因此不能说当前 N=16 已由动态效果定稿。

修复：所有候选面对相同真实帧、相同源时间；按共同回放评估候选增加/删除对有效覆盖、暂停尾部及事件确认的影响。可分批计算以限制资源，但不能把一次静态前 16 排名当成动态选 N 算法。

### R3 / P1：覆盖率把未观测时间当成有效识别时间

位置：`rtsp_annotator/ground_litter_profile_selector.py:609`。

汇总把上一条 `prior_allowed` 延续到下一条观测，只在间隔超过 300 秒时截断。没有根据观测节拍、结果有效期、实际可用区域限制这段有效时间。

反例时间点 0/2/4/204 秒，仅 4 次观测，200 秒无观测区间仍被累计，报告有效时间 202/206 秒、覆盖 0.98058。服务器盲测 3 个实际成功解码文件合计约 911.835 秒，报告 `observed_seconds` 却是 1461.614 秒。两段文件间空档被延续计入是主要原因。

修复：用真实可观测时间区间、节拍和结果过期边界积分；录像空档、解码失败、不可判断分别统计，不得延续旧状态冒充有效观测。需要面积权重时使用真正的 availability。修复前 0.9647/0.9453 均不作为验收覆盖率；不能凭现有汇总直接换算一个“正确数值”。

### R4 / P1：评估主链截断搜索预算，Top-K 之外可用 Profile 会一直查不到

位置：`scripts/evaluate_ground_litter_profile_bank.py:434`；关联 `ProfileSelector.plan_tick()`。

调用方将当前 Profile、粗排 Top-K、预留扩展候选拼接后截成预算长度。Selector 已推进搜索游标，后面的预留候选却可能未被真正检查；同时把“存在当前 Profile”误当成“当前仍可保持”。

反例 6 个 Profile 只有 p5 可用，粗排前三不可用，预算 4：连续 20 个 tick 均未检查 p5，最终无选中参考。这不是素材不足，而是公平扩展在接线后失效。

修复：按实际执行结果推进游标，预留预算不得被重复粗排挤占；当前保持条件使用真实评分；搜索一轮后的重试必须有明确策略。通过真正 `_run_tick()` 集成测试，不能仅验证 Selector 类。

### R5 / P1：没有实现“拉取→处理→删除”的有界流水线

位置：`scripts/build_ground_litter_profile_bank.py:346`、`:497`、`:519`、`:1055`。

工厂先 `materialize_remote()` 下载整批选中文件，再开始采样。遇到容量不足直接 `break`，后续仅处理已经 READY 的子集。采样后的释放调用仍在持有 lease 的上下文中，会被缓存保护拒绝，不能完成逐文件处理后的释放。

服务器这次通过配置 8 GiB 原始缓存容纳了 40 个 READY 文件，原始 PS 峰值约 2.858 GB；这证明批处理能跑完，不证明默认 1 GiB 下的有界流水线成立。扩大每天时槽后会截断素材或依赖上调配额，可能改变实际日期分区和环境覆盖。

修复：有界预取、消费、提交、释放流水线；退出 lease 后释放已提交文件；满额时等待消费而非丢弃后续计划。训练/校准/盲测分区先冻结，下载失败不能悄悄重定义分区。用总素材量明显超过缓存预算的集成案例验证全部计划最终消费、断点续跑和峰值上限。

### R6 / P1：小目标验证没有检查目标被检出，且本次 10 个目标全部在 ROI 外

位置：`scripts/evaluate_ground_litter_profile_bank.py:233`、`:392`、`:467`、`:506`、`:526`。

注入位置只在画面左上半区随机取值，不按 ROI/有效区域采样；按本次 seed、960×540 画布及真实 geometry 重现，10/10 注入框与 ROI 交集均为 0。

报告仅统计任意 tick 是否产生任意候选，没有把候选与注入框做空间匹配，还累加不同参考的候选。`_notify_switch()` 是空操作，没有接上事件 memory。因此当前测试连“小目标不被吞掉”的机制都没有实际证明，更不能证明发现、确认、清走的时延。

同时，缩放后 8 像素目标相当于原图约 21.3 像素；不能代表原图 6–8 像素碎垃圾。

修复：在实际可识别 ROI 内按原图尺寸注入并保存真值框；配对无目标基线，按位置匹配、逐例报告；用当前生效 Profile 和真实事件状态机验证，覆盖暂停与切换边界。低清图可用于粗检索，不能代替原尺寸小目标确认与 prior 分析。

### R7 / P1：背景合成未应用遮挡掩膜，噪声独立校准与局部可靠性没有落实

位置：`scripts/build_ground_litter_profile_bank.py:600`、`:640`、`:646`、`:684`、`:709`。

合成时每帧 mask 直接取整个 ROI，没有使用行人/车辆/context 或短时运动排除。噪声估计试图在本组构建帧中找构建集之外的块，最终回退到同一批构建帧；传入的 `calibration_blocks` 被丢弃。服务器 16/16 的 `noise_note` 均为 `low_support_used_all_blocks`。

发布的 `valid` 又是整个 ROI，未采用合成可用性及偏差诊断结果；服务器 16 张 valid mask 哈希相同。顶层 12 个低支持与嵌套 support 中 16 个低支持/未满足支持条件的口径不一致，不能据此声称已经落实更严格匹配与更小可用范围。

修复：按真实观测建立遮挡/可见性掩膜，跨独立时间块获得支持；从真正独立校准块估计噪声；局部有效范围和偏差处理必须影响发布资产/准入条件。低支持允许保留，但必须兑现保守使用约束。七天持续物体进入背景仍按用户要求允许。

### R8 / P1：噪声估计丢失每帧有效 mask，把未观测区域计为有效支持

位置：`rtsp_annotator/ground_litter_profile_background.py:553`、`:574`。

每帧 keep 只用于全局并集，随后每一块都给并集内所有像素赋权 1。某块被遮挡的像素仍进入残差统计和支持计数。

反例两个时间块仅左半/右半分别有效，每个像素真实支持数为 1，结果两侧均报 2。即使补上上游遮挡 mask，本缺陷仍会破坏其作用。

修复：保存并使用逐帧、逐块的有效 mask，支持计数及分位估计只纳入实际有效观测；对重复同块数据的聚合也必须遵守同一规则。

### R9 / P1：零可用性/坏帧仍可通过参考准入

位置：`rtsp_annotator/ground_litter_profile_analysis.py:347`；`scripts/evaluate_ground_litter_profile_bank.py:459`。

adapter 算出了 availability，却未将其与 corruption/geometry 状态纳入最终 match outcome。调用者又按 outcome 构造 `verified=True`，没有把真实可用比例传入选择决策。

反例给纹理帧显式标记 `corruption="known_bad_frame"`，结果 availability=0，但 enter/hold 均为 true。这样会虚增覆盖，后续也可能错误地恢复 prior。

修复：全局不可判断必须阻止准入与清走证据；局部不可判断只限制相应区域。真正全尺寸验证成功后才允许提交，不能用默认 verified 代替验证。

### R10 / P1：Bank prior 的残差和候选过滤不等价于计划中的生产分析链

位置：`rtsp_annotator/ground_litter_profile_analysis.py:79`、`:367`。

匹配评分与前景提取不是同一套补偿后的残差：前景直接比较原 reference/current；候选生成也没有原有大小/面积限制。

反例 1 像素噪点与 120×120 连通域都会生成候选。当前离线“有候选”不能外推到生产中既抑制极小误报、又保留规定尺寸小目标的效果。环境亮度变化也可能通过匹配却在未补偿的 prior 中形成大量前景。

修复：使用共享且有上限的光度补偿及残差定义，明确分析画布和尺寸换算，保留既定候选几何过滤；添加全局照度变化、噪点、大块变化、真实尺度小目标的回归，不通过抬高整图阈值掩盖问题。

### R11 / P2：每个文件独立建立配准基准，没有真正共同的 Bank 画布

位置：`rtsp_annotator/ground_litter_profile_sampling.py:768`、`:789`；`scripts/build_ground_litter_profile_bank.py:480`。

外层建立的共同基准没有传给 sampler；sampler 每个文件重新以第一张可用帧为配准参考，且没有传入 overlay 排除区。不同文件之间的像素偏移会保留，却被作为同一 view/ROI 发布。对数像素小目标，这不只是显示误差。

修复：使用训练集确定并冻结共同画布；每个文件映射到同一基准，保存变换与诊断，超限标记不适用。跨文件轻微平移的回归应检查背景残差、ROI 与小目标坐标，而非只验证同一文件内部配准。

## 交付表述需要同步纠正

1. 09-20 的 `files_evaluated=4` 不代表 4 个成功回放：时间线对应 3 个成功文件，另一个 gap 是 `DECODE_FAILED`。报告应分别列出计划、尝试、成功与失败。
2. 2560×1440 是 **16:9**，不是 4:3。已查看实际 ROI 复核图，不能用“录像 4:3”解释几何偏移，应核实截图裁边、变换或配置来源。
3. 工作目录峰值约 2.86 GB 不等于完整产物占用；仅本 Bank 的 64 个资产已经约 4.15 GB。原始缓存、工作目录、产物目录、内存应分别统计。
4. 查询 1/2/4 小时成功只能证明这些窗口可用；约 6.5 天可获取范围是本次观测，不是无限查询跨度或固定保留期的接口保证。
5. 当前素材量属于稀疏试跑。先修复算法、口径和有界资源处理，再扩大时槽采样，不能把追加数据当作上述缺陷的替代修复。

## 给实施者的修复顺序与验收步骤

### 第一步：冻结现状，修评估基础

- 保留 v1、报告和本评审反例，不覆盖旧结果。
- 修 R1/R2/R3/R4/R6；明确训练、校准、回归和新盲测分区。
- 将反例转成真实集成回归，特别覆盖实际 `_run_tick()` 和工厂编排。
- 对给定帧/时间序列手算有效时间，与程序完全对齐；不得仅断言 coverage 大于某常数。

### 第二步：修建库资产与资源流水线

- 修 R5/R7/R8/R11：有界消费、共同画布、逐像素支持、独立噪声统计和实际有效区域。
- 统一 low_support 定义，并验证低支持参考的更严格准入和可用范围确实生效。
- 总输入超过缓存配额的情况下，验证所有计划文件有明确最终状态，未因背压静默截断。

### 第三步：统一生产 prior 适配与离线验证

- 修 R9/R10，让离线验证使用方案二将实际调用的同一 adapter。
- 原分辨率运行 prior 和小目标验证；粗选低清尺寸与 full-size 验证分别记录耗时。
- 接入真实事件 memory，测试切换期间证据冻结、恢复、清走及事件身份连续性。这里允许离线执行，不要求提前接生产 API。

### 第四步：重建 v2，并用冻结资产做新的独立验证

- 在隔离目录重建，不覆盖 v1；每个 Profile 包含来源、支持范围、校准参数和完整哈希。
- 候选增删使用同一真实时间序列的指标差异；报告为何保留当前 N，不能用静态排名上限替代。
- 新盲测集不得参与选 N、阈值拟合或掩膜修订。若实际素材时间跨度不足，如实列出验证范围。
- 报告逐帧选择、真实时间积分、未知原因、有效面积、暂停、目标空间命中及事件确认；区别算法虚拟时钟结果与处理耗时。
- 保留原有 78 个测试，通过新增缺陷回归后再提交审核；最终在线整 tick 延迟、显存/内存和识别流卡顿仍属于方案二在线验收。

## ROI 决策

建议这轮修复先保留 r2 的业务覆盖范围，便于与 v1 对照。停车带边缘是否监测是业务取舍，不是当前验收失败的主要原因。先实现遮挡、支持不足和局部不可用处理，再依据逐区域误报/漏报证据决定是否内收；不建议通过内收 ROI 让错误的验收指标变好看。
